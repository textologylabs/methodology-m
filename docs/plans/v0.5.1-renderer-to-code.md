# Work Plan — v0.5.1: Renderer to Code + E2E Harness Seed

**Status:** Plan, ready to implement
**Branch:** `plan/v0.5.1-renderer-to-code` (this file), implementation continues on the same branch
**Target release:** v0.5.1 (or v0.6.0 if scope bleeds)
**Arc covers:** **I-049** (deterministic capabilities → code), **I-051** (`push_or_update_files`), **I-050 thin** (e2e harness seed)
**Prerequisite:** v0.5.0 shipped (I-036 complete)

---

## 1. Why this arc

v0.5.0 shipped the I-036 architectural refactor — `project.yaml` as a live config rendered into four topology-derived files via a chokepoint orchestrator (`render-topology-artefacts`). The live validation on real GitLab (MR !28) proved the critical path works end-to-end.

But the shipped implementation has three honest weaknesses captured in the v0.5.0 CHANGELOG:

1. **The renderer and its providers are SKILL documents, not executable code.** Determinism is agent-enforced, not mechanically enforced. Two agents reading the same SKILL could produce different bytes. The "byte-identical output" claim rests on agent discipline.

2. **`scm.push_files` can't update existing files** (latent bug in decompose-story S-4 pseudo-code). Worked around in v0.5.0 by using `git commit + git push`, but a future agent following the SKILL literally would hit this bug on the first real structural story.

3. **Integration coverage has big holes.** `bootstrap-root-repo` refactor was skipped entirely in the live test, `scaffold-repo` was mocked via direct API calls, `wire-orchestration` was never touched, and only the ADD structural operation was exercised.

v0.5.1's purpose is to close these as one coherent arc.

---

## 2. The architectural principle

**Deterministic → code. Interpretive → SKILL.**

This is the I-049 thesis, distilled. Apply it per capability and per provider:

- A step that is a pure function of its inputs (parse, schema-validate, resolve via lookup, render bytes, write files) → code (`.mjs`).
- A step that requires judgement (interpret story prose, decide sub-task boundaries, map ambiguous user intent to operations) → SKILL (markdown the agent reads).

This naturally produces a **hybrid**:

- **Capabilities that are 100% deterministic** (e.g. `render-topology-artefacts`) end up as thin SKILL stubs over a code body. The SKILL becomes a contract — parameters, conceptual purpose, invocation — and points at the `.mjs` that does the work.
- **Capabilities that are 100% interpretive** (e.g. parts of `decompose-story` that read story prose) stay as full SKILLs.
- **Most capabilities are mixed:** the SKILL orchestrates interpretive work and dispatches into code modules at every deterministic sub-step.

**File layout: code lives next to the contract it implements.**

```
.m/providers/compose/
  docker-compose.md      ← contract (thin: parameters, what, invocation)
  docker-compose.mjs     ← implementation, source of truth
  log-only.mjs

.m/providers/ci/
  gitlab.md              ← contract
  gitlab.mjs             ← implementation
  log-only.mjs

.m/capabilities/render-topology-artefacts/
  SKILL.md               ← thin contract + invocation pointer
  render.mjs             ← orchestrator, source of truth
```

**No new `m` CLI command is added in this arc.** The CLI surface is unchanged. The agent invokes the orchestrator directly (e.g. `node .m/capabilities/render-topology-artefacts/render.mjs --project-yaml=... --target-dir=...`) per the capability's invocation contract. The orchestrator imports the resolved provider modules at runtime.

## 3. Scope

### In scope

**I-049 (scoped to topology rendering)** — turn three deterministic units into code, co-located with their contracts:

- `.m/providers/compose/docker-compose.mjs` — pure function `(project) → [{path, content, mode?}]`
- `.m/providers/compose/log-only.mjs` — trace stub
- `.m/providers/ci/gitlab.mjs` — pure function `(project, scm) → [{path, content, mode?}]`
- `.m/providers/ci/log-only.mjs` — trace stub
- `.m/capabilities/render-topology-artefacts/render.mjs` — orchestrator (reads project.yaml, schema-validates, resolves providers, dispatches, writes files, reports)

The corresponding `.md` files shrink to **thin contracts**: parameters, conceptual purpose, invocation example. The behavioural detail moves to the `.mjs`. The `.md` no longer redescribes step-by-step rendering rules — those live in the code.

**I-051** — close the `scm.push_files` update lifecycle gap:

- Add `scm.push_or_update_files(repo, branch, files[], commit_message)` to `.m/providers/provider-interface.md`
- Implement in `.m/providers/scm/gitlab.md` (via GitLab commits API with mixed create/update actions)
- Implement in `.m/providers/scm/log-only.md` (trace stub)
- Update `decompose-story` SKILL S-4 to call the new function

The `scm` providers stay as SKILLs in v0.5.1 (they wrap MCP tool calls — the dispatch is mostly trivial but the platform-quirk handling is interpretive enough to stay markdown for now). I-049's reach into `scm.*` is a separate, later item.

**I-050 thin** — a repeatable end-to-end harness as a development script, not a CLI command:

- `scripts/e2e-harness.mjs` in the methodology-m repo (NOT under `.m/` — this tests M itself, it is not distributed to user projects)
- Drives the v0.5.0 live-validation flow programmatically: rewind workshop → render via the new orchestrator → push via the new `scm.push_or_update_files` → raise MR → wait on pipeline → assert green
- Used to validate I-049 + I-051 end-to-end before release
- Seed for future I-050 full (which will extend to bootstrap + scaffold + wire + all structural operations)

### Out of scope

- **Migrating every pure-function SKILL to code.** This arc does the topology renderer only. Other candidates (PAT→CAT compilation, readiness tracker ops, schema validation) remain filed under I-049 full for later.
- **Any new `m` CLI command.** The CLI surface stays exactly as v0.5.0 left it.
- **Non-ADD structural operations** (REMOVE, RENAME, MERGE, SPLIT, PORT-CHANGE). The harness will exercise ADD; other operations get their own fixtures and harness additions in I-050 full.
- **CI integration of the e2e harness** — running it on every methodology-m PR. Nice-to-have, not blocking.
- **External-package providers** — provider modules as installable npm packages. The interface must stay stable enough that this is *possible* in future, but shipping with external packages is not in v0.5.1.
- **Schema validation as a separate concern.** The orchestrator validates inline using `.m/schemas/project.schema.json`. No standalone validator command.
- **YAML parsing strategy for the orchestrator.** The orchestrator reads YAML directly (small dependency-free parser or a single dep). Keeps invocation simple — agents pass the path, orchestrator does the rest.

### Phase 1 — Design decisions (half-day)

Deliverables: decisions appended to this plan as a `## Decisions` section, then implementation proceeds.

Decisions to pin:

1. **Orchestrator invocation contract.** The agent invokes:
   ```
   node .m/capabilities/render-topology-artefacts/render.mjs \
     --project-yaml <path> \
     --target-dir <path> \
     [--targets compose,ci] [--dry-run]
   ```
   Stdout: one line per file written. Stderr: diagnostics. Exit codes: 0 success, 1 schema/validation error, 2 provider-not-found, 3 write error, 4 collision.

2. **YAML parsing.** Two options:
   - (a) Add `js-yaml` as a dev-only dep that gets vendored into `.m/`. Zero runtime cost for users (it's bundled).
   - (b) Hand-roll a minimal parser scoped to project.yaml shape.
   Recommend **(a)** — js-yaml is well-tested, project.yaml schema is permissive enough that hand-rolling is risk for no benefit.

3. **Provider module contract:**
   - Each provider is an ES module exporting a single function.
   - `compose` providers: `export function render_topology(project) → [{path, content, mode?}]`
   - `ci` providers: `export function render_pipeline(project, scm) → [{path, content, mode?}]`
   - Mode defaults: `0o644` for text, `0o755` for `scripts/*.sh`.
   - Pure functions — no filesystem, no network, no randomness, no timestamps.
   - Throw on invalid input; orchestrator catches and exits with code 1.

4. **Provider resolution rules** (codified in `render.mjs`, mirroring the SKILL):
   - `providers.compose` → explicit; fall back to `compose.integration.strategy` → `docker-compose`
   - `providers.ci` → explicit; fall back to `providers.scm`
   - Unknown provider name → exit code 2 with clear message.

5. **Provider discovery.** v0.5.1: hardcoded — orchestrator knows the four reference providers. Unknown names error. Filesystem scan / registry deferred to a later arc.

6. **SKILL doc shrink strategy.** Each `.md` keeps:
   - Title + one-sentence purpose
   - Function signature (parameters, return shape)
   - Invocation example
   - **Implementation pointer:** `Implementation: see <path>.mjs. The code is the source of truth for behaviour.`
   - Key invariants (the *what*, not the *how*)
   The detailed rendering rules currently in the `.md` move to JSDoc comments in the `.mjs` AND the test fixtures.

7. **Test layout.** Co-locate tests with code:
   - `.m/providers/compose/docker-compose.test.mjs`
   - `.m/providers/ci/gitlab.test.mjs`
   - `.m/capabilities/render-topology-artefacts/render.test.mjs`
   - Fixtures: `.m/test-fixtures/*.json` (parallel folder, kept out of dist via snapshot-dist filter)
   - Run via `node --test .m/`
   - `cli/test/cli.test.mjs` stays as-is (CLI tests).

8. **chmod and cross-platform.** `fs.writeFileSync(path, content, { mode: providerMode })`. Document Windows semantics differ; M is Linux/macOS focused.

9. **snapshot-dist update.** Add `.m/providers/compose/` and `.m/providers/ci/` whole-directory entries. Add a `*.test.mjs` exclusion filter so test files don't ship to user projects.

**Exit criterion:** every decision above is committed or explicitly deferred with a rationale.

Coding conventions:

- ES modules, Node ≥18
- Pure functions inside providers; all I/O in the orchestrator
- Clear error messages — every failure tells the user *what* and *why*

### Phase 3 — Tests (half-day)

Deliverables: co-located tests covering every provider branch and every orchestrator path.

Test fixtures (under `.m/test-fixtures/`):

- `todo-m-base.json` — 4-component topology (shell + mfe + api-read + api-write), no persistence
- `todo-m-with-persistence.json` — same + persistence block
- `todo-m-s01.json` — 5 components including analytics
- `todo-m-no-shell.json` — no embedded frontend-host (exercises the shell-lifecycle-conditional logic in `ci/gitlab`)

Tests per module:

- **`compose/docker-compose.mjs`:**
  - 4-component topology without persistence → assert `docker-compose.yml` shape
  - With persistence → assert `volumes:` block + `DB_PATH` env on backends
  - TODOM-S01 input → assert `analytics` service present
  - `embedded` vs `referenced` → assert `build.context` derivation
  - `integration-test.sh` → POSIX shebang, `check()` framework, one `check` call per component in declaration order, `DOCKER_GATEWAY` default

- **`ci/gitlab.mjs`:**
  - With embedded frontend-host → install/build/test jobs present, stages include them
  - Without embedded frontend-host → those jobs absent, stages shorter
  - Clone lines — one per referenced component in declaration order
  - `report-shadow-status.sh` — curl+REST pattern, `REPOS=` substituted correctly

- **`render.mjs`:**
  - Explicit `providers.compose` wins over `compose.integration.strategy`
  - `providers.ci` defaults to `providers.scm` when absent
  - Unknown provider name → exit code 2 with clear message
  - Write collision detection (compose + ci both claim same path → exit code 4)
  - `--dry-run` emits summary without writing
  - Schema validation failure → exit code 1, no writes

- **Determinism:**
  - Same input, two invocations → byte-identical output
  - Same input, different ordering of YAML keys at the top level → same output (order determined by manifest declaration, not YAML key order)

Test runner: `node --test .m/`.

**Exit criterion:** `node --test .m/` runs all tests green. Tests cover every provider branch.

## 6. Risks and open questions

### Risks

- **YAML dependency choice.** Phase 1 decision (a) introduces one dep. The vendoring path needs care so `.m/` stays self-contained when distributed. If vendoring proves messy, fallback to a hand-rolled parser scoped to project.yaml shape (still no runtime dep, more code surface).
- **MR !28 byte baseline divergence.** v0.5.0 was hand-validated; I may have produced bytes that don't exactly match the spec the new code now enforces. Phase 4 is the truth-finder. Code wins on legitimate corrections; CHANGELOG records them.
- **MCP tooling for `push_or_update_files`.** Current `mcp__gitlab__push_files` is create-only. Fallback documented in the gitlab provider spec is two-step per-file, which works but isn't atomic. File MCP follow-up if needed.
- **snapshot-dist exclusion logic.** The current entries copy whole directories with `cpSync`. Adding a filter for `*.test.mjs` may require a small custom copy walker. Manageable but a few lines.

### Open questions

- Should the orchestrator support a `--strict-deterministic` flag that errors on any non-deterministic input? **No** — determinism is unconditional.
- Should the harness exercise business decomposition (TODOM-001) or only structural (TODOM-S01)? **Structural only** in v0.5.1; business doesn't touch the renderer. Business coverage = I-050 full.
- Should we add a `.m/schemas/project.schema.json` validator as a separate module? **Defer.** Validation lives in the orchestrator for now.
