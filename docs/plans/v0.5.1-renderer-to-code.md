# Work Plan — v0.5.1: Renderer to Code + E2E Harness Seed

**Status:** Draft, not yet started
**Branch:** `plan/v0.5.1-renderer-to-code` (this file), implementation branch TBD
**Target release:** v0.5.1 (or v0.6.0 if the scope bleeds)
**Arc covers:** **I-049** (renderer as code), **I-051** (push_or_update_files), **I-050 thin** (e2e harness seed)
**Prerequisite:** v0.5.0 shipped (I-036 complete)

---

## 1. Why this arc

v0.5.0 shipped the I-036 architectural refactor — `project.yaml` as a live config rendered into four topology-derived files via a chokepoint orchestrator (`render-topology-artefacts`). The live validation on real GitLab (MR !28) proved the critical path works end-to-end.

But the shipped implementation has three honest weaknesses captured in the v0.5.0 CHANGELOG's "Known gaps" section:

1. **The renderer is a SKILL document, not executable code.** Determinism is agent-enforced, not mechanically enforced. Two agents reading the same SKILL could produce different bytes. The "byte-identical output" claim rests on agent discipline.

2. **`scm.push_files` can't update existing files** (latent bug in decompose-story S-4 pseudo-code). Worked around in v0.5.0 validation by using `git commit + git push`, but a future agent following the SKILL literally would hit this bug on the first real structural story.

3. **Integration coverage has big holes.** `bootstrap-root-repo` refactor was skipped entirely in the live test, `scaffold-repo` was mocked via direct API calls, `wire-orchestration` was never touched, and only the ADD structural operation was exercised.

Each of these is a real risk for the next user of I-036. v0.5.1's purpose is to close them as one coherent arc.

## 2. Scope

### In scope

**I-049 scoped** — move the topology renderer and its two pure-function provider namespaces into executable Node code in the `cli/` package:

- `cli/src/renderer.mjs` — orchestrator (project.json + target-dir → writes files)
- `cli/src/providers/compose/docker-compose.mjs` — pure function `(project) → [{path, content}]`
- `cli/src/providers/compose/log-only.mjs` — trace stub
- `cli/src/providers/ci/gitlab.mjs` — pure function `(project, scm) → [{path, content}]`
- `cli/src/providers/ci/log-only.mjs` — trace stub
- `m render-topology` CLI command — shells out from decompose-story S-2 and bootstrap-root-repo Step 6

**I-051** — close the `scm.push_files` update lifecycle gap:

- Add `scm.push_or_update_files` to `.m/providers/provider-interface.md`
- Implement in `.m/providers/scm/gitlab.md` (via GitLab's commits API with mixed create/update actions)
- Implement in `.m/providers/scm/log-only.md` (trace stub)
- Update `decompose-story` SKILL S-4 to call the new function

**I-050 thin** — first cut of the capability regression harness, as an executable that runs the same sequence we'd do by hand:

- `m test e2e --group <path>` command that drives the full from-scratch flow
- Hard-deletes the test group's repos (if they exist)
- Runs bootstrap → scaffold × N → wire-orchestration → decompose TODOM-001 → decompose TODOM-S01
- Waits on each pipeline, asserts green, reports pass/fail
- Used to validate I-049 + I-051 end-to-end before release
- Committed as the seed for future I-050 full

### Out of scope

- Migrating **every** pure-function SKILL to code. This arc does the renderer only. Other candidates (PAT→CAT compilation, readiness tracker ops, schema validation) remain filed under I-049 full for later.
- **Non-ADD structural operations** (REMOVE, RENAME, MERGE, SPLIT, PORT-CHANGE). The harness will exercise ADD; other operations get their own fixtures and harness additions in I-050 full.
- **CI integration of `m test e2e`** — running the harness on every methodology-m PR. Nice-to-have, not blocking. Captured separately.
- **External-package providers** — provider modules as installable npm packages. The interface must stay stable enough that this is *possible* in future, but shipping with external packages is not in v0.5.1.
- **Schema validation inside the renderer.** Kept as a separate `m validate-project` responsibility. The renderer trusts its JSON input.
- **YAML parsing inside the CLI.** The CLI takes JSON (via file or stdin). Callers — agents, or the `m` command that wraps them — are responsible for parsing YAML beforehand. Keeps `cli/` zero-dependency.

### Phase 1 — Design decisions (half-day)

Deliverables: a short design doc committed alongside this plan, or a decisions section appended here.

Decisions to pin:

1. **Renderer input format** — JSON via file (`--project-json <path>`) or stdin (`--project-json-stdin`). Agents parse YAML, pass JSON. Rationale: keeps `cli/` zero-dep, makes the CLI scriptable, simplifies testing. Alternative: depend on `js-yaml`. Pick one.

2. **CLI flag surface for `m render-topology`:**
   - `--project-json <path>` (required, or `--project-json-stdin`)
   - `--target-dir <path>` (required)
   - `--targets <list>` (optional, default: `compose,ci`)
   - `--dry-run` (optional, print what would be written without writing)
   - Exit codes: 0 = success, 1 = schema/validation error, 2 = provider-not-found, 3 = write error
   - Stdout: summary of files written (one per line)
   - Stderr: diagnostics + errors

3. **Provider module contract:**
   - Each provider is an ES module exporting a single function
   - `compose` providers export `render_topology(project) -> [{path, content, mode?}]`
   - `ci` providers export `render_pipeline(project, scm) -> [{path, content, mode?}]`
   - Mode defaults to `0o644` for text, `0o755` for `scripts/*.sh`
   - Providers are pure — no filesystem, no network, no randomness, no timestamps
   - Providers throw on invalid input (the renderer catches and exits with code 1)

4. **Resolution rules (duplicated from I-036 spec, codified in renderer.mjs):**
   - `providers.compose` → explicit; fall back to `compose.integration.strategy` → `docker-compose`
   - `providers.ci` → explicit; fall back to `providers.scm`
   - Unknown provider → fail with clear error

5. **Provider discovery:**
   - v0.5.1: hardcoded — renderer knows about `compose/docker-compose`, `compose/log-only`, `ci/gitlab`, `ci/log-only`
   - Unknown provider name → error "provider not found"
   - Future (not this arc): filesystem scan of `cli/src/providers/<category>/` or registry

6. **SKILL doc strategy:**
   - Keep `.m/providers/compose/docker-compose.md` and `.m/providers/ci/gitlab.md` as **agent-readable contracts** describing what the provider does
   - Add a new section at the top: `**Implementation:** See `cli/src/providers/compose/docker-compose.mjs`. This document describes the provider's contract; the code is the source of truth.`
   - Manual sync burden documented; automated contract-test-from-doc deferred

7. **chmod and cross-platform:**
   - `fs.writeFileSync(path, content, { mode: providerMode })` for executable bit
   - Document that Windows semantics differ; M is currently Linux/macOS focused

**Exit criterion:** every decision above is either committed or explicitly deferred with a rationale.

### Phase 2 — I-049 core implementation (1 day)

Deliverables: working `m render-topology` command.

Tasks:

1. Create `cli/src/providers/compose/docker-compose.mjs` — port `compose/docker-compose.md`'s rendering rules to Node. Every branch of the role → content mapping. Handle persistence. Component order preservation. Build-context derivation per type.
2. Create `cli/src/providers/compose/log-only.mjs` — emit two `{path, content}` entries with trace markers so tests can assert the renderer dispatched correctly.
3. Create `cli/src/providers/ci/gitlab.mjs` — port `ci/gitlab.md` to Node. Long file — shell lifecycle conditional on embedded frontend-host, orchestration jobs, conditional clone lines per referenced component, scm-aware report script.
4. Create `cli/src/providers/ci/log-only.mjs` — trace stub.
5. Create `cli/src/renderer.mjs` — orchestrator. Reads JSON input, resolves providers, dispatches, collects outputs, writes files, prints summary.
6. Wire into `cli/bin/m.mjs` as the `render-topology` subcommand. Follow whatever pattern Phase 0 discovered.

Coding conventions:

- ES modules, Node ≥18
- Zero dependencies outside Node stdlib
- Pure functions inside providers; all I/O in the orchestrator
- Clear error messages (every failure tells the user what and why)
- Byte-deterministic output (same input → same output every run, no timestamps, no randomness)

**Exit criterion:** `m render-topology --project-json fixtures/todo-m-s01.json --target-dir /tmp/out` runs to completion and writes 4 files. No tests yet, just the happy path.

### Phase 3 — Unit tests for the renderer (half-day)

Deliverables: `cli/test/renderer.test.mjs` and `cli/test/providers/*.test.mjs`.

Test fixtures (new files in `cli/test/fixtures/`):

- `todo-m-base.json` — 4-component topology (shell + mfe + api-read + api-write), no persistence
- `todo-m-with-persistence.json` — same + persistence block
- `todo-m-s01.json` — 5 components including analytics
- `todo-m-no-shell.json` — a topology without an embedded frontend-host (to exercise the shell-lifecycle-conditional logic in `ci/gitlab`)

Tests per provider:

- **compose/docker-compose:**
  - 4-component topology without persistence → assert docker-compose.yml shape
  - Same with persistence → assert volumes block + DB_PATH env
  - TODOM-S01 input → assert analytics service present + depends_on updated
  - `type: embedded` vs `type: referenced` → assert build.context derivation
  - `integration-test.sh` → assert POSIX shebang, check() function present, one `check` call per component in declaration order, DOCKER_GATEWAY default

- **ci/gitlab:**
  - Topology with embedded frontend-host → assert install/build/test jobs present, stages include install/build/test
  - Topology without embedded frontend-host → assert those jobs absent, stages shorter
  - Clone lines — one per referenced component in declaration order
  - `report-shadow-status.sh` content — curl+REST pattern, REPOS substituted correctly

- **renderer orchestrator:**
  - Explicit `providers.compose` wins over `compose.integration.strategy`
  - `providers.ci` defaults to `providers.scm` when absent
  - Unknown provider name → exit code 2 with clear message
  - Write collision detection (compose and ci both claim the same path → error)
  - `--dry-run` emits summary without writing

- **determinism:**
  - Same input, two invocations → byte-identical output
  - Same input, different ordering of component yaml keys → same output (order determined by project, not by JSON key order)

Test runner: `node --test cli/test/` (existing convention).

**Exit criterion:** `npm test` in `cli/` runs all tests green. Tests cover every provider branch.

### Phase 5 — I-051 push_or_update_files (half-day)

Deliverables: provider interface update + SKILL updates.

Tasks:

1. Add `scm.push_or_update_files(repo, branch, files[], commit_message)` to `.m/providers/provider-interface.md`. Document that it handles both create and update atomically in a single commit.
2. Update `.m/providers/scm/gitlab.md` — specify the GitLab commits API call:
   ```
   POST /projects/:id/repository/commits
   {
     branch: <branch>,
     commit_message: <message>,
     actions: [
       { action: "create" | "update", file_path: ..., content: ... }
     ]
   }
   ```
   The provider determines `create` vs `update` per file by first checking if the file exists on the branch (via `mcp__gitlab__get_file_contents`).
3. Update `.m/providers/scm/log-only.md` — trace stub.

If new MCP function is needed, file it as a follow-up (implementation is outside methodology-m) and have the gitlab provider spec describe the two-step workaround (`create_or_update_file` per file) as the interim implementation.

**Exit criterion:** decompose-story S-4 can be followed literally by an agent and will succeed for both business and structural stories.

### Phase 6 — I-050 thin e2e harness (1 day)

Deliverables: working `m test e2e` command.

Tasks:

1. Design the harness invocation:
   ```
   m test e2e --group <gitlab-group-path> [--project-name <name>] [--keep-on-fail]
   ```
   - `--group` is the target test group (e.g. `methodology-m/todo-m-workshop`)
   - `--project-name` defaults to a computed name (e.g. from the current git branch)
   - `--keep-on-fail` leaves state for manual inspection on failure

2. Harness flow (as Node code in `cli/src/commands/test-e2e.mjs`):
   - **Step 0 — Precondition:** confirm the target group is empty or can be cleaned. If repos exist, fail with a message pointing to `--rewind` or manual deletion.
   - **Step 1 — Story Zero:** read `workshop/jira/TODOM-000/TODOM-000.md` as the input
   - **Step 2 — Bootstrap:** shell out to the agent (or, for v0.5.1, invoke the SKILL steps programmatically where possible — the renderer is code now, but bootstrap-root-repo still has agent-driven parts like SCM repo creation). Minimum viable: wrap the key operations (create root repo, render topology, push seed files) into orchestration code. Falls back to documented manual steps where full automation isn't ready.
   - **Step 3 — Scaffold:** for each referenced component, run scaffold-repo equivalents
   - **Step 4 — Wire:** run wire-orchestration equivalents (webhooks, triggers, secrets)
   - **Step 5 — Smoke:** push a trivial change on a managed repo, wait for shadow pipeline, assert green
   - **Step 6 — Business story:** decompose TODOM-001, assert MR raised, pipeline green
   - **Step 7 — Structural story:** decompose TODOM-S01, assert MR raised, pipeline green, rendered files byte-match expectations
   - **Step 8 — Teardown:** close MRs, delete feature branches (optionally delete repos with `--clean-teardown`)
   - **Step 9 — Report:** print a structured pass/fail summary, return non-zero on any failure

3. **Key realization about scope:** full automation of bootstrap + scaffold + wire is ambitious for v0.5.1 because those capabilities still have SCM provider calls that agents normally dispatch via MCP. The harness either:
   - **Option A:** Invokes the agent to execute each capability, then waits for it to complete. Needs a protocol for "capability done, move on". Messy.
   - **Option B:** Bypasses the agent for provider calls and calls the GitLab API directly from Node. Simpler but duplicates logic the SKILLs describe.
   - **Option C:** Scopes the harness more narrowly to *the parts that are already code* — the renderer. Asserts the renderer output against real GitLab by pushing to a branch and waiting on a pipeline, similar to what v0.5.0 validation did by hand.

   **Plan decision:** Start with Option C for v0.5.1. It's the smallest useful slice. Full bootstrap/scaffold/wire automation becomes I-050 full in a later release.

4. Under Option C, the harness becomes narrower:
   - Precondition: rewind existing workshop to `story-zero-complete` tag
   - Render topology for TODOM-S01 via the new `m render-topology` command
   - Create scratch branch on root repo
   - Push rendered files via the new `scm.push_or_update_files` (tests both I-049 and I-051 simultaneously)
   - Raise MR via `scm.create_merge_request`
   - Wait on the MR pipeline
   - Assert every job green
   - Close MR + clean up branches
   - Return pass/fail

5. This narrow harness is essentially "the I-036 live validation done again, but scripted and repeatable." Ship it.

**Exit criterion:** `m test e2e --group methodology-m/todo-m-workshop` runs to completion and returns 0. Running it twice in a row returns 0 both times.

## 5. Risks and open questions

### Risks

- **Bootstrap/scaffold/wire automation may turn out to be larger than Option C accounts for.** The plan hedges by starting with Option C; if Option C proves insufficient, we file the full version as I-050 full and keep v0.5.1 scope honest.
- **MR !28 byte baseline may differ from code output in surprising ways.** My v0.5.0 hand-writing could have drift I didn't catch. If the code wins, we correct the record; if it loses, we fix the code. Either way, Phase 4 is the truth-finder.
- **MCP tooling for `push_or_update_files`** may not exist — the current `mcp__gitlab__push_files` is create-only. The fallback in the gitlab provider spec is two-step (per-file `create_or_update_file`), which still works but isn't atomic. Document the gap; file as a separate MCP tooling item if needed.
- **`snapshot-dist.mjs` may need changes** to properly include `cli/src/providers/` in the npm package. Phase 0 inspection should catch this.

### Open questions

- Do we want to add a `.m/schemas/project.schema.json` validator as part of this arc, or defer? Recommendation: **defer.** Validation is orthogonal to rendering and deserves its own item.
- Should the renderer support a `--strict-deterministic` flag that errors on any non-deterministic input? Recommendation: **no**, the determinism should be unconditional — there's nothing non-deterministic to opt out of.
- Should `m test e2e` support multiple targets (gitlab + github + local-sim)? Recommendation: **no in v0.5.1**, gitlab only. Multi-target is I-050 full.
- Should the harness also exercise the business decomposition (TODOM-001), or only the structural one? Recommendation: **structural only** in v0.5.1, because the business path doesn't touch the renderer. Business coverage is I-050 full.

## 7. Sequencing note

The phases are roughly sequential but some parallelism is possible:

- Phase 5 (I-051) can run in parallel with Phase 2/3 since it touches different files.
- Phase 6 (harness) depends on Phase 2 being complete (the harness invokes `m render-topology`).
- Phases 7 and 8 are strictly sequential after 6.

For a single-threaded implementation pass, run phases in order. If sharing with a second contributor, Phase 5 can be peeled off and done in parallel.
